## What the Public Contract Actually Says

1. **Capacity is a byte count, not an entry count.** API 2.0.3 `Cache.Options.capacity?: number` is documented as “The capacity in bytes” with a default of **“10 MB”**. Neither the declaration nor the current public page gives the numeric value of `Cache.DEFAULT_CAPACITY`, spells out decimal versus binary MB, or precisely defines whether keys/index/filesystem overhead count. Do not silently equate that public text with 10,000,000 or 10,485,760 bytes. Tinycast chooses the latter, but that is reference behavior, not Raycast runtime proof. [D1: lines 1072–1078; W1: `Cache.Options`]
2. **Static and instance properties are different.** The exact 2.0.3 class declares **static** getters `STORAGE_DIRECTORY_NAME: string` and `DEFAULT_CAPACITY: number`. It declares **instance** getter `storageDirectory: string`, described as the full directory path holding the data. There is no declared static `Cache.storageDirectory`. The private `directory` field is not a public instance property. The public constructor option `directory?: string` is the parent directory and is explicitly deprecated; it still exists in this version. No value for the static directory-name constant is specified. [D1: lines 1001–1014, 1068–1071]
3. **Namespaces have documented filesystem meaning.** Cache is shared between an extension's entry points by default; a namespace uses a subdirectory. Actual values are documented as separate files in the extension's support directory, with only a lightweight index in memory. A path getter must identify actual storage, not an invented or unused folder. [D1: lines 980–990, 1061–1066; W1: introduction]
4. **LRU is real behavior, not another name for rejecting overflow.** A `get` is the data-access operation; `has` explicitly checks without affecting LRU access. `set` removes least recently used entries when configured capacity is exceeded. The sources do not specify tie breaking, the exact outcome for one value larger than the entire capacity, how eviction notifications are grouped, the numeric treatment of zero/fractional/invalid capacities, or cross-process/cold-reopen recency rules. Those details must not be invented as verified parity. [D1: lines 1015–1034; W1: `Cache#get`, `Cache#has`, `Cache#set`]
5. **Current web documentation is corroboration, not a 2.0.3 pin.** The fetched page agrees on bytes, “10 MB”, namespace sharing and LRU. It omits the deprecated directory option, static getters and instance path getter. Its constructor snippet requires an argument, while the pinned declaration says `constructor(options?: Cache.Options)` and its own example uses `new Cache()`. Use the pinned declaration for the target signature. [D1: line 1010; W1: signature/example/options]

## What Pinned Tinycast Does—and Does Not Prove

Read-only source inspection, not third-party execution or an implementation to copy:

- `Scripts/raycast-runtime/src/api/system.js:58–75` sets an instance capacity to `options.capacity ?? 10 * 1024 * 1024`, picks `options.namespace ?? "default"`, and creates an in-memory map from Swift's boot snapshot. That is **10 MiB** in this implementation. The six public methods are bound so detached callbacks work.
- Lines 78–92 leave `has` and `get` as map lookups; `set` coerces keys and values to strings, persists asynchronously and notifies. There is **no capacity check, LRU touch, ordering or eviction** in these operations. The file's only capacity use is the constructor assignment at line 61. No directory option handling, storage-directory getter or the two static getters are implemented here.
- Lines 115–138 issue fire-and-forget host writes and load boot namespace contents. `Tinycast/Features/Extensions/Service/ExtensionStorage.swift:118–139` stores namespace dictionaries; its persistence section writes the extension's combined JSON atomically after coalescing writes. It does not enforce this Cache capacity or maintain LRU either.
- The pinned extension documentation identifies `extension-data/<safe name>.json` as persistent LocalStorage, Cache and preferences storage (`docs/features/extensions.md:825`). That layout is not the public separate-file/subdirectory contract. It is also not TockTeam's existing format.

**Conclusion:** Tinycast is useful evidence of a chosen binary default and synchronous facade/write-behind approach. It supplies no proof that capacity, directory or LRU semantics are complete. Porting its unused capacity field would merely repeat a gap. Do not copy its write-behind/error-swallowing or combined format into TockTeam.

## Existing TockTeam Data Must Stay Protected

Current source inspection at the saved baseline:

- Host state is `<installRoot>/state/<validated-extension-ID>.json`; the new stable support folder is the separate `<ID>.support` sibling. The manager binds the state path privately to the child. Cache and LocalStorage formats are not moved into support by `.8.2.7`. [S3: `statePath`, lines 223–229; S4: child environment, line 99; S5: lines 72–87]
- Raw Cache is one string-valued JSON object. Its **entire UTF-8 JSON file is limited to 65,536 bytes (64 KiB), with at most 256 entries across default and all named namespaces together**. New writes allow at most **4,096 UTF-8 bytes per string value**, not 4,096 characters. Public keys must be nonempty and at most 128 JavaScript string units; namespaces may be empty (the default) or strings of at most 128 units. Named cache keys are encoded hashes, not caller filesystem paths. Encoded keys are 135 characters and membership checks require their complete valid hash shape; valid public prefix-shaped keys remain public. [S1: lines 22–27, 61–86]
- Existing valid raw files can contain legacy strings larger than 4 KiB, empty public keys and other previously visible strings. Loading does not impose the new-write value bound. A follow-up must not truncate or retroactively invalidate them merely because new writes are smaller. Existing named entries and public prefix-shaped keys must remain reachable. [S1: `load`, `publicValues`; T1: lines 13–46]
- The **typed LocalStorage sidecar and the legacy safety snapshot are the same versioned file**, `<rawPath>.local-storage.v1.json`, not two additional stores. Before its existence, public legacy raw strings are the LocalStorage view. Before the first valid default-Cache mutation, that visible legacy namespace is published and checked in this sidecar before the raw Cache file changes. Typed LocalStorage writes also populate this file without retyping or modifying raw Cache. Named-cache-only writes do not create it. [S1: lines 13, 40–73; T1: lines 13–133]
- The sidecar separately has **64 KiB / 256 entries**; its new string writes have the **4 KiB** value bound. Preservation includes larger legacy strings that still fit its file bound. JSON wrapper overhead can make the safety copy fail even when the raw object fits; such a failure preserves raw data and reports failure before destructive Cache changes. The two files can use approximately **128 KiB in aggregate**, plus transient publication files—not one unchanged 64 KiB total quota. [S1: lines 40–58, 108–121; T1: quota/failure tests]
- Existing no-follow bounded regular-file reads, validation, exclusive private temporary publication, fsync/rename and conservative failure outcomes must remain. Invalid/unreadable/linked sidecars do not silently become empty stores; failure may leave a harmless recoverable safety copy but must not report a failed mutation as successful. This is not a multi-file atomic transaction or a same-user OS sandbox. [S1; S6; T1]
- Current Cache public methods preserve their tested namespace/subscriber isolation, quiet clear, detached callbacks and stale unsubscribe behavior. The facade takes only `namespace`; JavaScript callers' `capacity`/`directory` fields are currently ignored, and static/path getters are absent. Raw `get`/`has` do no recency writes. Hard file/entry limits reject new writes rather than evicting. These are existing documented compatibility gaps, not an accepted implementation of the wider Cache contract. [S2: lines 400–413; S1: lines 80–99; T2]

## Smallest Honest Choices

These are proposals only, not new authority or a selected design.

1. **Keep the Current Limits and Make Unsupported Requests Clear.** Recommended first, if old data and unchanged budgets are the priority. Explicitly reject unsupported capacity/custom-directory controls rather than silently ignoring them, and keep unproved getters/constants and LRU on the open ledger. No new data format, metadata file, directory, budget or eviction; all existing data stays in place. This is a truthful smaller compatibility subset, **not completion of Cache parity**. The implementation would need a failing-first caller-visible check only after approval.
2. **Add Small Cache Limits Without Increasing the Data Budget.** After a separate bounded design approval, accept only explicitly supported byte-capacity requests no larger than the existing budget and apply access-based trimming only to the selected namespace on an explicit write. Keep the shared raw **64 KiB / 256-entry / 4 KiB-new-value** hard limits; do not evict other namespaces to make room. Preserve legacy LocalStorage before any default eviction, and leave old bytes untouched on construction/read. The least-change recency variant uses at most **256 in-memory markers per raw store**, shared by its Cache instances: **zero additional disk bytes, no read-time filesystem writes**, but order resets on restart and old unranked data must not be auto-evicted without an explicit approved policy. A persistent variant would add a separately bounded file and publication/failure policy; its numeric quota is deliberately unapproved, so it cannot ship under this preparation. Neither variant automatically provides the documented 10 MB default, separate-file layout, real storage-directory getter or deprecated custom-directory behavior. Do not present it as full Cache compatibility. Shared-instance different-capacity behavior still needs a decision; a fresh per-instance snapshot must not overwrite another instance's newer data.
3. **Give Cache a Separately Approved Storage Budget.** Required to approach the wider public contract. First verify or explicitly settle the numeric default and approve a dedicated per-extension backend, its file/value/entry/index/aggregate limits, supported directory choices and recency/eviction rules. Use only admitted owned locations; a custom path must not grant arbitrary API-managed filesystem mutation. Old raw Cache, typed LocalStorage/safety data and user-created support files must remain recoverable and unchanged unless a separately approved explicit mutation/migration says otherwise. Eager import, moving named hashes into directories, read-side rewrites, automatic eviction of unranked legacy entries or overwriting a pre-existing support/cache folder is **not** implied by this option. A new cache budget is additive to existing files; name the total before approving it. This is the largest choice and needs a preservation-first design before implementation, not a quiet quota bump.

For a persistent/full option, a `get` may need to publish recency metadata even though data bytes do not change; that is a new read-time write, with failure outcomes and a bounded bookkeeping quota that require approval. A new data budget plus any index/journal/safety/publication files must all be included in the total. Multiple Cache instances and restarts must use one coherent admitted store rather than stale write-behind snapshots; neither durable recency nor cross-process ordering/locking is established by current behavior. Supporting both is additional design and verification work, not a side effect of exposing a numeric capacity.

**Decision requested:** choose the first narrow honesty-only slice, a specifically limited trimming slice, or a separately budgeted wider backend. No source changes begin until the conductor selects and bounds one. Recommendation: approve Choice 1 now, keep Choices 2/3 as distinct decisions, and reconcile other safe public contracts while numeric/default/layout details remain unverified.
