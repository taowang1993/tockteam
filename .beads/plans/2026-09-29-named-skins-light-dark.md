# Plan: Light and Dark for Every Named Skin

## Problem and Design Read

Today, choosing Deep Current, Jade Circuit, or Ember Dusk pins a dark palette; choosing Porcelain pins a light palette. The existing Appearance controls then appear not to work. People want variety **and** control over Light, Dark, or System. The Obsidian Settings screenshot separates its base color scheme from theme selection; use that distinction, not its marketplace implementation or visual styling.

TockTeam Settings, TockCoder, TockTutor, TockLauncher, Web, and TUI must remain recognizably the same product. This is a targeted evolution of the existing skin feature, not a new theme engine.

## User-Visible Result

- **Original**, **Deep Current**, **Jade Circuit**, and **Ember Dusk** remain the choices. Remove Porcelain from the supported gallery because Original already offers Light.
- Appearance offers **Light**, **Dark**, and **System** for *every* choice in Desktop and Web. Changing Appearance keeps the chosen skin selected; changing skins keeps the Appearance selection. System follows OS mode changes.
- Each named skin has its own genuinely distinct light palette, not a white screen with a recolored accent. Its existing dark palette remains recognizable. Both modes keep the sidebar/titlebar brighter than the editor, with readable labels, focus and selected states.
- TUI offers Light and Dark variants in its native theme picker. It retains the pinned renderer and its own selection authority; automatic OS-follow in the terminal is not added.
- Saved dark skins retain their current dark appearance on first upgrade. A saved Porcelain choice becomes Original Light. Original's current Light, Dark, and System behavior remains unchanged.

## Implementation Decisions

1. **Keep one owner.** Retain `@tockteam/skins`, its Host preferences route, the existing Settings gallery, `plugins/skins/src/skins.ts` as the only catalog, DSH Profile + Loader composition, and semantic `--dsw-*` tokens. Do not install `dsh-dream-skin`, create a second theme loader, or build a community theme market in this work.
2. **Separate the two choices at the DSH seam.** The pinned DSH `0.1.2-rc.1` `ThemeRuntime` already owns the built-in Light/Dark/System preference and its General → Appearance controls. Its documented `overrideTokens(source, tokens)` accepts `{ light, dark }` for each semantic token and follows System mode. Apply one disposable, skin-scoped paired token layer while a named skin is selected; keep the DSH built-in preference active so its Appearance buttons remain selected and persisted. Clearing the skin removes the layer. Avoid registering a second selectable theme per mode or intercepting the inherited Appearance buttons. Guard against a synchronous `theme/change` / override feedback loop and do not shade unrelated third-party themes.
3. **Keep stable skin-family IDs.** Preserve the three existing named IDs and stored `activeId`; make each catalog entry hold Light and Dark semantic token sets and mode-specific previews. Retain the existing dark values where possible, project both sets to TUI, and keep `data-tockteam-skin` as the family ID. Let `plugins/skins/src/client/tailwind.css` continue to map shared shell/editor roles rather than adding route-specific color overrides. Do not use media-query `dark:` for application appearance.
4. **Migrate without a surprise reset.** Keep the `skins.json` data root, `activeId`, and `fallbackTheme` compatibility. On first upgrade, preserve a legacy selected dark skin's visible Dark mode even if its old `fallbackTheme` remembered Original Light; retain the latter until the user changes Appearance or returns to Original. Record the one-time migration explicitly so a later intentional Light selection is never forced back to Dark. Recognize a legacy Porcelain ID long enough to map it to Original Light, including native TUI `theme.json`; do not treat the old file as corrupt or erase other settings. Only remove a retired TUI theme file when its bytes match a known generated file; preserve customized files. Test restarts and repeated migration.
5. **Preserve the Launcher bridge.** Today `src/launcher-theme.ts` infers skin from the active theme ID, which will now be `light` or `dark`. Read the selected family from the existing `desktopSkins` service, the resolved mode from DSH, and project both through the unchanged restricted Launcher theme message. Subscribe to both sources; use the catalog's matching palette in `src/launcher.ts`. No new IPC privilege or exposed browser capability.
6. **Respect surface authority.** Desktop/Web Appearance owns their mode; TUI's native picker owns the TUI mode when it has a saved choice. The shared `skins.json` records the selected family and migration compatibility, not a competing live browser theme engine. Do not force a browser appearance choice merely because TUI has a different saved mode.

## Risks and Non-Goals

- **Mode and selection drift:** DSH preference and a selected family are distinct; an override must not reset the Appearance row or loop on `theme/change`. The pinned service contract plus focused lifecycle tests guard this.
- **Palette regression:** a light accent or overlay can obscure controls even when token names look correct; measure *computed* colors/contrast and visually review all six states, including portals and selected/checked controls.
- **Compatibility:** retired Porcelain and native TUI files may be customized. Keep recoverable stored data and touch only recognized generated artifacts; verify one-time migration and downgrade-sensitive behavior before shipping.
- **Scope boundary:** Obsidian's community theme market is evidence that choice matters, not permission to add theme downloads, execute third-party CSS/plugins, add wallpapers, change DSH/renderer ownership, or alter the pinned runtime in this plan.
